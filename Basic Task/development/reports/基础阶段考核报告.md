## 1. 项目与应用场景

**服务对象**：澄禾工作室（虚构），共 8 人，同时在线 1—4 人。

**业务需求**：

- 办公类：邮件撰写、会议纪要与进度整理、制度与条款问答、入职流程清单
- 编程类：代码审查、缺陷定位与修复、程序设计

**请求特点**：

| 类型 | 输入规模 | 输出规模 | 任务数 |
| --- | --- | --- | --- |
| 纯提示词（P01—P04） | 141—164 token | 200—800 token | 4 |
| 关联文档（D01—D04） | 1837—2299 token | 400—3000 token | 4 |
| 关联源文件（C01—C02） | 1657—1672 token | 800—3000 token | 2 |

办公任务占 6/10，编程任务占 4/10。成员按需手动发起请求，测试中用固定任务列表组织负载以保证可重复。

**优化目标**：在保证 10 个规定任务全部可服务的前提下——

1. 降低多并发场景的 TTFT 与请求完成耗时；
2. 提升生成吞吐；
3. 扩大 KV 容量（以 token 为单位），并控制显存占用。

**为什么最终把 KV 容量作为主要目标**：在测试过程中发现，按常规配置（`-c 8192 -np 4`）启动时，每 slot 只有 2048 token，**而规定任务中最长的 D01 输入就有 2299 token，直接返回 `exceed_context_size_error` 而失败**。也就是说容量而非速度才是首先暴露的瓶颈，这决定了优化方向的优先级（详见第 7 节改动 3）。

**模型选择依据（显存 → 模型 → 上下文的关系）**

- 显存总量 12227 MiB，扣除桌面占用后可用约 11 GiB。Qwen3-8B Q4_K_M 权重占 **4455 MiB**（见日志 `CUDA0 model buffer size = 4455.34 MiB`），是能在该显存下完整驻留且保持较强中文办公与代码能力的档位。
- 选择 8B 而非更小模型：第 8 节的输出检查说明，规定任务需要多条款引用与代码缺陷定位，模型能力直接决定得分；0.6B/4B 档位在这两类任务上不可靠。
- 选择 8B 而非 14B：14B Q4_K_M 权重约 9 GB，扣除后 KV 与计算缓冲不足 2 GiB，无法同时满足 4 并发与足够上下文，属于"能加载但不可用"。
- 模型全部计算层与 KV 缓存驻留 GPU：日志显示 `offloaded 29/29 layers to GPU`，且 KV 缓冲位于 `CUDA0`。
- 按任务要求**关闭主机 RAM prompt cache**：服务启动参数固定带 `--cache-ram 0`，启动日志出现 `--cache-idle-slots requires --cache-ram, disabling`，确认主机侧 prompt cache 已关闭，缓存工作集驻留显存。

**关于硬件的说明**：本机为笔记本 GPU，散热与功耗受限，绝对吞吐低于同型号台式机。报告中的比较均为同一台机器、同一模型、同一负载下的相对比较，结论不依赖绝对数值。重复测试的波动状况见第 6 节。

## 5. 指标与测试方法

| 指标 | 定义与公式 | 采集位置 |
| --- | --- | --- |
| **TTFT** | 客户端提交请求 → 首个**非空**生成内容，**包含**客户端可观察的排队与传输时间。服务端在提示词处理阶段会先发送一个 `content` 为空的角色块，该块不计入首 token | 客户端 `time.perf_counter()` |
| **TPOT（服务端）** | `predicted_ms / predicted_n`。仅覆盖生成阶段，**排除首 token**，也不含排队与提示词处理 | 服务端响应 `timings` 字段 |
| **TPOT（客户端）** | `(total_ms - ttft_ms) / (output_tokens - 1)`，排除首 token，含传输 | 客户端计算 |
| **吞吐** | ① 解码吞吐 = 成功请求生成 token 总数 / 服务端生成耗时之和（`sum(predicted_ms)`）；② 请求吞吐 = 成功请求数 / 墙钟时间（含排队与提示词处理） | 客户端 + 服务端 timings |
| **请求完成耗时** | 客户端提交 → 流结束，含排队、提示词处理、生成与传输；给出中位数与 P95 | 客户端 |
| **显存占用** | 模型加载后与测试过程中的峰值 | `nvidia-smi` 1 秒采样，`results/gpu/<run_id>.csv` |
| **KV 容量（token）** | 区分配置总容量、每 slot 可用容量、实测可用容量；分槽方式与 KV 精度由启动日志确认 | 启动日志 + `/props` + 容量探测 |
| **成功率与恢复耗时** | 成功 = 取得非空生成内容；分母为逻辑请求数；恢复耗时 = 从触发重启到 `/health` 就绪 | 逐请求记录 + 恢复测试记录 |

**P95 采用最近秩法**（nearest-rank），对每轮 10 个请求的小样本比插值法更稳健。

**token 统计**：不数流式数据块。一个数据块可能包含多个 token，因此输出 token 数一律取服务端 `timings.predicted_n`；输入 token 数取 `timings.prompt_n + timings.cache_n`，并用 `/apply-template` + `/tokenize` 独立核对。`cache_n` 即被复用的提示词 token 数。

**预热与重复**：每种核心配置执行 3 轮相同负载；轮次之间间隔 2 秒；同一配置的 3 轮在同一服务进程内连续执行（不重启），因此第 2、3 轮存在 slot 级提示词复用，这一点在报告中被明确标注，不作为性能提升计入。

**失败、取消与重试的统计口径**：

| 状态 | 处理方式 | 是否计入分母 |
| --- | --- | --- |
| `success` | 取得非空生成内容 | 是 |
| `failed` | 收到错误响应或连接失败，按上限重试 | 是（按逻辑请求计一次） |
| `timeout` | 超过请求超时上限 | 是（按逻辑请求计一次） |
| `cancelled` | 提交前检测到服务中断，未发送 | 是（按逻辑请求计一次） |

每个逻辑请求有唯一 `request_id`，重试记录在同一 request_id 的 `attempts` 中，汇总按逻辑请求计数一次，`retry_count` 单独统计，避免重复计数。

## 6. 基线结果

**基线配置**：`-ngl 99 -c 16384 -np 4 -cb -fa off -ctk f16 -ctv f16 -b 2048 -ub 512 -t 8`（关闭 Flash Attention，KV 为 f16，4 slot，每 slot 4096 token，`--cache-ram 0`）

| 运行编号 | 配置 | 并发 | 成功/总请求 | TTFT 中位数/P95 (ms) | TPOT 服务端 (ms) | 解码吞吐 (tok/s) | 请求吞吐 (req/s) | 完成耗时中位数/P95 (ms) | 显存峰值 (MiB) |
| --- | --- | ---: | ---: | --- | ---: | ---: | ---: | --- | ---: |
| `R20261016-130612-baseline-c1` | baseline | 1 | 30/30 | 53 / 698 | 12.3 | 81.2 | 0.401 | 2432 / 3099 | 10490 |
| `R20261016-130731-baseline-c4` | baseline | 4 | 30/30 | 630 / 2275 | 24.0 | 41.5 | 0.667 | 4679 / 7504 | 10474 |

原始数据路径：`results/runs/R20261016-130612-baseline-c1/requests.jsonl`、`results/runs/R20261016-130731-baseline-c4/requests.jsonl`

### KV 容量口径（基线）

| 项目 | 值 | 证据 |
| --- | --- | --- |
| KV 精度 | K f16 / V f16 | 日志 `K (f16): 1152.00 MiB, V (f16): 1152.00 MiB` |
| 分配方式 | 按 slot 分槽，非共享池 | 日志 `kv_unified = 'false'`，`4/4 seqs` |
| 每 slot 可用容量 | 4096 token | 日志 `4096 cells, 36 layers, 4/4 seqs` |
| 配置总容量 | 16384 token | 4096 × 4 |
| KV 显存（日志实测） | 2304.00 MiB | 日志 `CUDA0 KV buffer size = 2304.00 MiB` |
| KV 显存（按架构推算） | 2304.00 MiB | 36 层 × 8 KV 头 × (128+128) × 2 字节 = 144 KiB/token；× 16384 = 2304 MiB |
| 实测可用容量 | 输入 4008 token（4996 token 时失败） | `results/capacity_baseline.json` |
| 模型权重 / 计算缓冲 | 4455.34 MiB / 308.01 MiB | 日志 `CUDA0 model buffer size`、`CUDA0 compute buffer size` |

**主要瓶颈分析**

1. **瓶颈一：上下文容量，而非速度。** 基线每 slot 4096 token，实测最大可用输入 4008 token，而规定任务中最长的 D01 已占 2299 token，余量仅约 1.7 倍。考题允许单条输入达到 50,000 token，一旦文档变长就会直接 `exceed_context_size_error` 失败。在更保守的 `-c 8192 -np 4` 配置下（每 slot 2048），D01 与 D02 **立即失败**，错误为 `request (2299 tokens) exceeds the available context size (2048 tokens)`。
2. **瓶颈二：多并发下 TTFT 与吞吐劣化明显。** 并发由 1 升到 4 后，TTFT 中位数由 53 ms 升到 630 ms（约 12 倍），解码吞吐由 81.2 降到 41.5 tok/s（约 −49%）。前者是 4 个请求竞争 4 个 slot 时的排队与提示词处理等待，后者是 4 条序列共享同一条解码带宽的结果。
3. **瓶颈三：计算缓冲偏高。** 关闭 Flash Attention 时 `CUDA0 compute buffer size = 308.01 MiB`，是 KV 之外可观的显存开销。

## 7. 优化过程与效果

| 改动编号 | 发现的问题 | 改动及配置差异 | 预期作用 | 实际效果 | 资源与输出变化 | 是否保留 |

### 代码审查题的参考缺陷清单（用于核对 C01/C02 输出）

以文件开头的功能约定为准，`编程输入03-ticket_stats.py` 共存在 13 处缺陷，按修复优先级：

**P0 崩溃类**

1. 空输入：`int(sum(hours) / len(records))` → `ZeroDivisionError`（约定应返回 `total=0`、四状态 0、`by_owner={}`、`average=None`）
2. 直接索引 `record["owner"]`：缺 `owner` 键 → `KeyError`
3. 直接索引 `record["status"]`：缺 `status` 键 → `KeyError`
4. `by_status[status] += 1`：未知状态、含空格或大小写变化 → `KeyError`
5. `datetime.fromisoformat` 无保护：时间格式非法 → `ValueError`
6. `render_summary` 中 `sorted(by_owner)`：键含 `None` 时 → `TypeError: '<' not supported between 'str' and 'NoneType'`
7. `ticket_hours` 直接索引 `created_at`/`closed_at`：缺键 → `KeyError`

**P1 计数口径类**

8. 完全未按 `id` 去重，也未跳过空/缺失编号，却用 `len(records)` 作 `total`。样例数据实测：`total` 报 5（应 4）、`closed` 报 3（应 2）、`Chen` 报 3（应 2）
9. `owner` 未规范化：`None` 与 `"   "` 成为两个独立键，均未归入 `unassigned`；`" Chen "` 未去空格
10. `status` 未 `strip`/`lower`，未把未知值映射为 `other`

**P2 耗时口径与格式类**

11. 平均耗时分母用 `len(records)` 而非有效 closed 工单数；且仅用 `record.get("closed_at")` 判断，**未检查 status 是否为 closed**——未关闭工单若带遗留 `closed_at` 会被计入（实测返回 1 小时）
12. 非 closed 工单 `hours.append(0)`，把 0 计入均值，系统性拉低平均值
13. 无时区时间未过滤（实测计入 2 小时）、`closed_at` 早于 `created_at` 未过滤（实测计入 **−1 小时**，负数进入均值）；`int()` 截断而非保留两位小数；无有效 closed 工单时应为 `None` 而非 `0`

样例数据的期望值：`total=4`、`by_status={open:1, processing:1, closed:2, other:0}`、`Chen.total=2`、`average_closed_hours=3.38`；原程序实际输出 `total=5`、`closed=3`、`Chen.total=3`、`average=1`。

**检测机制**：`/health` 返回 `{"status":"ok"}` 且模型已加载时判定为就绪；连续失败或进程已退出时判定为异常。就绪确认在重启后轮询 `/health`，只有返回就绪才允许继续提交请求。

**三类请求的处理方式**：

| 请求类别 | 处理方式 |
| --- | --- |
| **等待请求**（已入队、尚未发送） | 每轮开始前检查服务就绪；若检测到服务中断，置位停止标志，未发送的请求标记为 `cancelled`，`error_type=service_interrupted`，**不重复计数** |
| **已发送请求**（在途） | 中断时归为 `failed`，`error_type=service_unavailable` / `http_error`，记录提交与失败时间点 |
| **失败请求** | 按 `max_retries` 做有限次重试（本任务上限 1 次），重试前退避 1 秒；每次尝试记入同一 `request_id` 的 `attempts`，汇总时**按逻辑请求计数一次**，`retry_count` 单独统计 |

## 10. 总结与改进

**完成情况**

- 在 WSL2 + CUDA 的 WSL 环境中完成 llama.cpp 源码编译与 GPU 推理部署，模型全部 29 层计算层与 KV 缓存驻留 GPU，并按要求关闭主机 RAM prompt cache。

- 完成容量边界验证与异常恢复测试。

**有效优化**

1. **Flash Attention 是收益最大的一项改动**：并发 4 下 TTFT P95 −25.5%，解码吞吐 +22.9%，同时计算缓冲减少 200 MiB。仅改一个配置项即获得该效果，与考题"有时候仅仅改动配置参数就能实现性能大幅提升"一致。
2. **KV 量化 q8_0 用约 6% 的吞吐代价换来 KV 显存减半**（2304→1224 MiB），并由此把每 slot 上下文从 4096 扩到 8192 token。
3. **扩容本身几乎无吞吐代价**：上下文翻倍后吞吐变化在 ±3% 波动范围内，但实测可用输入容量翻倍（4008→7941 token）。

**发现的问题**

- **容量优先于速度**：最初的常规配置根本无法服务最长的规定任务。若不先做容量探测，容易在"已经能跑"的错觉下把时间花在微小提速上。
- **模型的条款引用存在系统性缺口**：D03/D04 均漏引跨章节的前置条件与安全要求（D03、D05、A01），而非格式问题。
- **模型能定位口径类缺陷但修复时会退回同一错误**：C02 生成的平均耗时仍用错分母（1.69 vs 3.38），且未实现 `None` 语义。这类真实代码修复必须人工复核计算口径。
- **本机为笔记本 GPU**，功耗与温度波动使并发 1 下的 TTFT 极差达到约 13%（绝对值 7 ms）；并发 4 下相对稳定（约 3%）。绝对性能数值不应与台式机横向比较。

**下一步可实现的改进**

1. **slot 数与容量的联合调优**：本次受 12 GiB 显存限制，未能在保持每 slot 8192 token 的前提下把 slot 数提到 8。可尝试更低的 KV 精度（`q4_0` / `iq4_nl`）或更小量化档位，在容量与并发间寻找更优组合，并按第 5 节同样的口径记录容量与输出效果。
2. **投机解码与批处理参数**：引入 draft 模型或调整 `-b`/`-ub`，观察并发 4 下吞吐与 TTFT 的变化。
3. **缓存复用单独量化**：本次观测到同一 slot 内的提示词复用（D01 第 2、3 轮 `cache_n=2209`，TTFT 由首轮 863 ms 降至 63 ms / 60 ms）。可把"跨轮复用"作为独立实验变量，统计命中率与复用 token 比例。
4. **对办公类输出引入结构化校验**：把条款编号、日期、负责人等抽取为结构化字段再比对，比当前的关键词匹配更能定位"漏引哪一条"。

## 11. AI 辅助开发与开源项目使用

**使用的开源项目**

| 项目 | 版本/commit | 用途 |
| --- | --- | --- |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) | `005a1e127a84cc75bb66be11b43e4f0773564e53` | 推理引擎，`llama-server` 提供推理、`/slots`、`/metrics`、`/props`、`/tokenize`、`/apply-template` 等接口；按官方 `tools/server/README.md` 确认参数语义 |
| Qwen3-8B | `Qwen3-8B-Q4_K_M.gguf`，SHA256 `d98cdcbd…` | 推理模型（Qwen 官方 GGUF） |

llama.cpp 以源码方式获取并按 `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=120` 自行编译，未修改引擎源码；本项目的开发内容全部位于 `development/` 下的 Python 模块与配置中。

**AI 辅助编码的使用范围**

- 使用 AI 辅助编码工具完成 `src/antlab/` 下各模块的编写、调试与重构，以及报告文字的组织。
- AI 参与的部分：模块骨架与数据类、流式客户端与时间点采集、指标与百分位实现、并发执行器与重试去重逻辑、前端页面、检查器骨架、本报告的初稿。

**核验方式（关键结论均经过独立核验，未直接采信生成结果）**

1. **提示词解析**：`tests/test_units.py` 断言恰好解析出 10 个任务、6 个任务带关联文件、文件 SHA256 与磁盘一致、`关联文件：`元数据行已从正文剥离、输入顺序为「系统消息 → 资料区 → 任务区」。
2. **指标口径**：单元测试用固定输入断言 TTFT 仅统计成功请求、`by_status` 分类正确、重试按逻辑请求计一次、解码吞吐以服务端生成耗时之和为分母、空输入不触发除零。
3. **token 计数**：不采信流式块数，一律取服务端 `timings`；另用 `/apply-template` + `/tokenize` 独立核对输入 token 数。
4. **KV 容量**：三个配置下**按 GGUF 架构参数独立推算的 KV 大小与启动日志实测值完全一致**（f16@16384：均为 2304.00 MiB；q8_0@16384：均为 1224.00 MiB；q8_0@32768：均为 2448.00 MiB），互相验证。
5. **性能数据**：全部由本目录代码实际产生并保存为 `requests.jsonl`，报告中的每张汇总表都由 `python3 run.py tables` 从原始记录重新计算生成，可逐条回算。
6. **模型输出**：`checks.py` 直接从输出文件中抽取 C02 的代码，在独立子进程中实际执行 18 项边界用例，而不是只做文字判断；办公任务按输入资料中的客观事实与条款编号逐条比对。
7. **开发过程中由实测发现并修正的实现缺陷**（均保留在开发过程中）：`to_dict()` 漏带 `content` 导致输出未落盘；报告汇总按「配置+并发」分组时未包含 `load_id`，把性能负载与质量负载混算；`kvlog` 正则空格数不匹配导致 KV 详情漏抓。这些问题都是通过实际运行数据发现的，而非阅读代码发现。

## 12. 复现与数据索引

```bash
# 1. 编译推理引擎（CUDA 后端，sm_120）

cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CUDA_ARCHITECTURES=120 -DLLAMA_CURL=OFF

# 2. 获取模型（校验 SHA256 应为 d98cdcbd…）
#    Qwen3-8B-Q4_K_M.gguf -> /root/models/

python3 run.py env                 # 采集环境与模型校验值
```
